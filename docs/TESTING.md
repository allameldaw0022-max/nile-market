# 19. Testing Strategy

> قاعدة المواصفات: «بعد التنفيذ، شغّل الاختبارات وأصلح الأخطاء بدل
> الاكتفاء بتقرير عنها». ميزة بلا اختبار = ميزة غير مكتملة.

## 19.1 الأدوات

| الطبقة | الأداة | أين |
|---|---|---|
| Unit | **Vitest** | منطق المال · الصلاحيات · آلات الحالة · التحقق |
| Integration | Vitest + Supabase محلي | Server Actions فوق قاعدة حقيقية |
| Database / RLS | **pgTAP** | داخل Postgres — تشغيل حقيقي لا محاكاة |
| E2E | **Playwright** | تدفقات المستخدم كاملة |
| Accessibility | `axe-core` داخل Playwright | كل صفحة رئيسية |
| Performance | Lighthouse CI | عتبات تُفشل البناء |
| Security | `gitleaks` · `npm audit` · `get_advisors` | CI |

> لا توجد اليوم أي اختبارات ولا CI — تُبنى من الصفر في المرحلة 0.

## 19.2 ★ اختبارات عزل المتاجر (الأولوية القصوى)

**معيار القبول: متجر A لا يصل إلى بيانات متجر B — أبدًا، بأي طريق.**

بذرة ثابتة: متجر A (مالك + 4 موظفين بأدوار) · متجر B (مالك) · عميل لكل
متجر · شريك · موظفو Admin بصلاحيات مختلفة.

```ts
// tenant-isolation.spec.ts — يولَّد آليًا لكل جدول مستأجَر
const TENANT_TABLES = ['products','categories','orders','order_items',
  'customers','payments','coupons','inventory','store_settings',
  'store_domains','store_members','support_tickets','audit_logs', ...];

for (const table of TENANT_TABLES) {
  test(`${table}: عضو A لا يقرأ صفوف B`, async () => {
    const { data } = await asUser(ownerA).from(table).select('*').eq('store_id', storeB);
    expect(data).toEqual([]);
  });
  test(`${table}: عضو A لا يُدرج بـstore_id = B`, async () => {
    const { error } = await asUser(ownerA).from(table).insert({ store_id: storeB, ... });
    expect(error).toBeTruthy();
  });
  test(`${table}: عضو A لا يحوّل صفًا من A إلى B`, async () => {
    const { error } = await asUser(ownerA).from(table)
      .update({ store_id: storeB }).eq('id', rowInA);
    expect(error).toBeTruthy();
  });
}
```

**مسارات الهجوم المختبَرة عبر HTTP (لا عبر القاعدة فقط):**
1. `/dashboard/orders/<order-of-B>` بجلسة A ⇒ 404.
2. Server Action بـ`storeId` مزوّر في الـpayload ⇒ `FORBIDDEN`.
3. استدعاء PostgREST مباشر بـanon key على جدول خاص ⇒ صفر صفوف.
4. `Host: store-b.nilemarket.online` مع كوكي جلسة A ⇒ لا تسريب لوحة.
5. `/_sites/x` من دومين المنصة ⇒ 404.
6. Signed URL لملف متجر B ⇒ رفض.
7. RPC مالي بمعرّفات متجر B ⇒ استثناء.

## 19.3 الصلاحيات

**اختبار مصفوفي مولَّد**: لكل (دور × مورد × عملية) في
[`PERMISSIONS.md`](./PERMISSIONS.md) ⇒ حالة اختبار.

- `customer_service` لا يحذف منتجًا ولا يرى `cost_price`.
- `products` لا يرى هاتف العميل.
- `orders` لا يعدّل إعدادات المتجر.
- `manager` لا يرى `bank_accounts` ولا يدير الدومين.
- موظف Admin بـ`support:view` فقط: `/admin/payments` ⇒ 404،
  و`payments` عبر API ⇒ صفر صفوف.
- **اختبار تكافؤ**: `STORE_ROLE_PERMISSIONS` في TS == `app.role_default_permissions` في SQL.
- لا أحد يرفع دوره أو يمنح دورًا أعلى من دوره.

## 19.4 المال

### العمولات
1. 20,000 − 5,000 ⇒ عمولة **7,500** بالضبط.
2. احتساب مزدوج لنفس الدفعة ⇒ صف واحد.
3. لا دفع ⇒ لا عمولة.
4. استرداد كامل ⇒ عكس كامل، والأصل سليم.
5. استرداد جزئي 40% ⇒ عكس 40%.
6. تخفيض باقة ⇒ لا عمولة سالبة.
7. تغيير النسبة ⇒ الماضي محفوظ بـ`rate_applied`.
8. طلبا صرف متزامنان ⇒ واحد ينجح.
9. `UPDATE/DELETE` على `commission_ledger` ⇒ استثناء لكل دور.
9b. **فصل المهام (D29/D30):** اعتماد استرداد أو صرف بنفس مستخدم
    `requested_by` ⇒ انتهاك `CHECK` · اعتماد بنفس `initiated_by`
    (الشريك/العميل/التاجر) ⇒ انتهاك · **نفس المحاولة عبر
    `service_role` تفشل أيضًا** (تجاوز RLS لا يتجاوز القيود) ·
    طلب شريك بحالة `submitted` لا يُنشئ أي قيد مالي.
10. متجر بشريكين ⇒ انتهاك `unique`.

### الدفع والطلبات
11. عميل يرسل `delivery_fee: 0` ⇒ الخادم يستخدم سعر المنطقة الحقيقي.
12. عميل يرسل `price` أقل ⇒ يُتجاهل تمامًا.
13. ضغط مزدوج على «تأكيد الطلب» ⇒ **طلب واحد** (نفس `order_id`).
14. كوبون مستخدم فوق حده ⇒ رفض.
15. كوبون منتهٍ / خارج نطاقه ⇒ رفض.
16. خصم > المجموع ⇒ `total >= 0`.
17. دفعة بنفس `idempotency_key` ⇒ صف واحد.
18. استرداد > مبلغ الدفعة ⇒ رفض.
19. تعديل `amount` بعد `paid` ⇒ استثناء.
20. `DELETE` على `ledger_entries` ⇒ استثناء.
21. شراء متزامن لآخر قطعة ⇒ طلب واحد ينجح والمخزون لا يصبح سالبًا.

## 19.5 الاشتراكات والحدود
- حد 50 منتجًا: الـ51 يُرفض في **القاعدة** (لا الواجهة فقط).
- إنشاءان متزامنان عند الحد ⇒ واحد ينجح.
- Downgrade ⇒ **لا يُحذف** منتج؛ الجديد فقط يُمنع.
- انتهاء ⇒ لا حذف متجر/منتجات/طلبات/سجلات مالية (فحص بعد الكنس).
- إعادة التفعيل ⇒ كل شيء يعود كما كان.
- انتقالات الحالة بـpg_cron صحيحة مع تعديل زمني مصطنع.
- Upgrade ⇒ الميزات سارية **فورًا**.
- `custom_domain.enabled=false` ⇒ الإضافة مرفوضة برسالة ترقية واضحة.
- **D31:** `commercial_launch_enabled` يُرفض تفعيله ومفاتيح
  `plan_entitlements` غير مضبوطة (`configured_at is null`)، وتُعرض
  حالة «Plan Configuration غير مكتمل».

## 19.6 الطلبات والمخزون
- كل انتقال مسموح ينجح، **وكل انتقال ممنوع يُرفض** (مصفوفة كاملة).
- `completed → ...` مرفوض دائمًا.
- تغيير الحالة بلا صلاحية ⇒ رفض.
- كل انتقال يكتب صفًا في `order_status_history`.
- المخزون: حجز → خصم → إرجاع، بالأرقام الصحيحة في كل مسار.
- `UPDATE inventory.quantity` مباشرة ⇒ مرفوض (الحركات فقط).

## 19.7 الدومينات
**D33:** الـslug القديم يعيد 301 داخل 12 شهرًا · بعد انقضاء الحجز
يتوقف التوجيه ويصبح الاسم متاحًا · خلال الحجز لا يأخذه متجر آخر.
**D32:** بعد Anonymization تبقى `orders.contact_name/contact_phone`
و`invoices.snapshot` **دون تغيير** (اختبار مقارنة قبل/بعد).

دومين واحد لمتجرين ⇒ رفض · تحقق بتوكن خاطئ ⇒ فشل · إزالة ثم إعادة
إضافة ⇒ دورة تحقق جديدة إلزامية · `is_primary` واحد فقط · غير الأساسي ⇒
301 · Host مجهول ⇒ 404 · متجر موقوف ⇒ صفحة الإيقاف · canonical يستخدم
الدومين الأساسي.

## 19.8 الدعم
عزل التذاكر بين المتاجر · **صاحب التذكرة لا يقرأ `support_internal_notes`
بأي طريق** · انتقالات الحالة · المرفقات (نوع/حجم/وصول) · Rate Limiting ·
منع تكرار الإشعارات · Pagination مع 1000 رسالة.

## 19.9 الاستيراد والتصدير
CSV صالح · صفوف غير صالحة تُعرض ولا تُستورد · CSV بـ10k صف ⇒ Job خلفي ·
حقن الصيغ (`=cmd`) ⇒ معالَج عند التصدير · ترميز عربي UTF-8 سليم ·
الاستيراد يحترم حد الباقة · تصدير بلا صلاحية ⇒ رفض.

## 19.10 المصادقة
تسجيل/دخول/خروج · تأكيد البريد · استعادة وإعادة تعيين · Google OAuth ·
Rate Limiting على الدخول · رسالة موحّدة لا تكشف وجود البريد · إلغاء
الجلسات · «خروج من كل الأجهزة» · لا ترقية دور عبر بيانات التسجيل.

## 19.11 E2E (Playwright)
1. **رحلة التاجر:** تسجيل → إنشاء متجر (Wizard كامل) → منتج → نشر →
   استقبال طلب → تغيير الحالة → فاتورة.
2. **رحلة الزبون (زائر):** فتح متجر → بحث → منتج → سلة → Guest Checkout
   → نجاح → متابعة بالرقم.
3. **رحلة الاشتراك:** اختيار باقة → طلب + إثبات → اعتماد Admin → ميزات
   سارية → عمولة الشريك مسجَّلة.
4. **رحلة الشريك:** رابط → تسجيل تاجر → إسناد → دفعة → عمولة → طلب صرف →
   اعتماد → سجل.
5. **رحلة الدعم:** فتح تذكرة → تعيين → رد → ملاحظة داخلية (غير مرئية
   للتاجر) → حل → إغلاق.
6. **رحلة الموظف:** دعوة → قبول → صلاحيات دوره فقط.
7. **رحلة الدومين:** إضافة → تعليمات → تحقق → تفعيل → 301.

كلها على: **موبايل (390px)** وتابلت (768px) وديسكتوب (1280px).

## 19.12 الاستجابة والأداء
كل صفحة على 3 مقاسات · بلا تمرير أفقي · أهداف لمس ≥44px · RTL سليم ·
Lighthouse ≥ 90 للمتجر · عدد الاستعلامات ضمن العتبة · حجم الحزمة ضمن
الميزانية.

## 19.13 الأخطاء والتعافي
انقطاع الشبكة أثناء الحفظ ⇒ لا فقدان بيانات · إعادة الإرسال بنفس
`idempotency_key` ⇒ لا تكرار · فشل خدمة غير أساسية (بريد) ⇒ **لا ينهار
النظام** · `maintenance_mode` ⇒ صفحة صيانة والـAdmin يعمل · فشل Job ⇒
إعادة محاولة ثم تنبيه.

## 19.14 CI

```yaml
on: [push, pull_request]
jobs:
  quality:   # lint · typecheck · gitleaks · حظر استيراد service client
  unit:      # vitest
  database:  # supabase start → migrations → pgTAP (RLS + الصلاحيات)
  e2e:       # playwright على بيئة preview
  perf:      # lighthouse-ci (يفشل عند الهبوط)
  advisors:  # supabase get_advisors (security + performance)
```

**بوابة الدمج:** لا دمج إن سقط أي اختبار عزل أو صلاحيات أو مالي.

- البذرة تُنشئ: متجرين · 5 أدوار · شريكًا · عملاء · طلبات في كل حالة ·
  اشتراكات في كل حالة · تذاكر في كل حالة.
